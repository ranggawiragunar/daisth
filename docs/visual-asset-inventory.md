# Daisth Visual Asset Inventory

Audit-only snapshot of the checked-out repository, prepared 2026-10-15. Product files and visual assets were inspected but not changed. This report is the only intended change from this audit.

## Scope and counting

- **87 raster/vector image files:** 42 under `assets/` and 45 under Android/iOS native asset directories. The detailed inventory below records every physical image file, including generated platform scale variants. Font files and text documentation are recorded separately because they are not image visuals.
- **75 unique code icon constants** across 112 source occurrences: 34 Material `Icons.*` constants and 41 Phosphor constants. Same constants reused in different widgets are one identity; selected/unselected Phosphor variants are listed together.
- **10 known runtime file-art placements** across seven `Image.asset` callsites/consumers: the mark is shown in About and the license dialog, the routine visual is supplied by two demo routines, and the shared empty-state widget has two known consumers. Runtime placements exclude native config copies and user-provided photos/attachments.
- **7 physical in-app artwork files** are recommended as 3D replacement candidates (six logical artworks because Today has a light/dark pair). There are 75 code glyph identities recommended to remain vector.
- **6 Daisth logo source files** (three PNG/SVG pairs) are brand protected. Native review covers **55 physical image files**: 45 platform catalog/resource files plus 10 launcher/splash master files, grouped into launcher, splash, and notification families.
- **Potentially unused:** 27 `assets/` image files have no detected runtime reference or native configuration role. Confidence varies and is stated per group; do not treat this audit classification as deletion approval.
- Of those, **16 physical image files** are classified `REMOVE_UNUSED_CANDIDATE`; brand source and native source files remain in their protected review classes even when not rendered in Dart.
- **Broken references:** none found in the inspected Flutter source, pubspec asset directories, Android XML, or iOS asset catalog manifests. Asset use through user-selected attachment files and account photo URLs is runtime user content, not a Daisth artwork asset.

The `sips` metadata inspection returned pixel dimensions and alpha flags for rasters. SVG dimensions are their `viewBox` dimensions, not pixels. File sizes in the detailed table are bytes. Native image files repeat at platform density names; some catalog entries point to repeated full-resolution files, which is captured in the duplicate section.

## Risk notes

- Today uses a full-card background with `BoxFit.cover`, `Alignment.centerRight`, card clipping, and a left gradient/text area. Narrow widths crop the scene; EN/ID copy length can change the gradient-text overlap. The image is opaque, so transparent padding is not currently relied upon.
- Onboarding and empty-state art share vertical space with localized copy. Scrolling/available viewport height can alter the overall composition even though the image itself is centered and not overlaid.
- Routine art source is 1448×1086 but appears at 76×76. It may be oversized for its current display and finer 3D details may become indistinct; layout is fixed square.
- Empty-state PNGs are 2048×1536 and render between 148–220 px on a 4:3 source. They are heavily downscaled; test silhouette at final display size during any future design pass.
- Several artwork variants are PNG/SVG alternatives, while Flutter currently renders only PNG. Replacing the PNG without checking the SVG source relationship could leave inconsistent artifacts for a later vector implementation.
- Native splash catalog scale-named iOS images are same pixel dimensions and bytes. Do not infer platform effective size from filenames alone.
- No `BoxFit`/size is explicitly set for the brand mark in the license dialog; default `Image.asset` fitting applies. The wordmark and other branded assets are also high-resolution source exports.
- Routine user attachments and account photo URLs are dynamic user content; their appearance can vary and should not be mistaken for a reusable Daisth illustration.
- Icon-package glyphs are functional or category symbols. They are not candidate illustrations, even when drawn in a large size (for example, the Dhikr completion check).

## Future asset naming and formats

Suggested future in-app structure only (not created): `assets/visuals/3d/{onboarding,today,routines,routine_detail,reflection,reader,zikir,history,settings,location,empty_states}/`. Use predictable snake-case names such as `today_focus_light.webp` and `today_focus_dark.webp`; keep shared artwork without a theme suffix only when truly identical. Record intended display ratio and alpha in the design handoff.

- Photographic/rendered opaque scenes: WebP for app delivery when platform fidelity is verified; retain a lossless master outside delivery if needed.
- Transparent cutout illustrations: WebP with alpha where supported by the target Flutter pipeline, or PNG for predictable alpha fidelity. Keep at least 2× max display dimensions.
- Logos, motifs, and scalable simple geometry: SVG/vector source; Flutter needs an approved rendering path before runtime SVG usage. Rasterize only for fixed native requirements.
- Functional and system glyphs: existing package vector glyphs; native launcher and notification formats follow platform requirements.
- Native app icons and splash images: platform catalog/native format generated from reviewed masters, with separate light/dark/adaptive handling.
